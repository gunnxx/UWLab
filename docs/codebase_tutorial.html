UWLab · OmniReset · Isaac Lab 3.0

UWLab Codebase Tour

How the repository is organised, how a reinforcement learning environment is assembled from configuration, how the policy is trained, and which script starts it all.

This tutorial is written for someone who has used a reinforcement learning library before but is opening this repository for the first time. It follows the peg insertion task from the OmniReset project because that task exercises every part of the code. The same structure applies to the other five tasks and to the newer Unitree G1-D variant. Each chapter ends with the files you should open to see the ideas in code.

1. The repository at a glance

UWLab is an extension layer on top of NVIDIA Isaac Lab, which is itself a layer on top of Isaac Sim. Nothing in this repository talks to the physics engine directly. Instead, the repository provides configuration objects and small Python terms that Isaac Lab's managers call during simulation. Understanding that division of labour is the single most useful idea for reading the code: Isaac Lab owns the loop, and UWLab owns what happens inside each step.

The four packages under source/ are separate Python distributions with their own pyproject.toml. They are installed together by uwlab.sh, which is the repository's wrapper around Isaac Sim's bundled Python interpreter. When a script is started with python inside the Forge image, that interpreter is already the right one.

Finally, docker/forge/ packages everything into one image and provides shell pipelines that chain the tools together with a cache on a shared disk.

2. The environment

2.1 The manager-based pattern

Isaac Lab offers two ways to write an environment. A direct environment is a Python class whose author writes the step function by hand. A manager-based environment is assembled from configuration: the author declares a scene and a list of terms for each manager, and the generic ManagerBasedRLEnv class calls those terms in a fixed order. UWLab uses the manager-based pattern everywhere, which is why most task files contain almost no imperative code. They are dataclasses that name functions.

Figure 2 shows one control step. The policy emits an action at the control rate. The action manager turns it into joint targets and writes them to the simulator, which then advances the physics several times. Afterwards the managers compute observations, rewards, and termination flags, and the event manager resets whichever environments finished. The ordering matters when you read a term: a reward term that reads last_action sees the action that was just applied, and an observation term runs after the physics has settled for the step.

2.2 Reading a task configuration file

Open source/uwlab_tasks/uwlab_tasks/manager_based/manipulation/omnireset/config/ur5e_robotiq_2f85/rl_state_cfg.py. It is long, but it is organised as a sequence of small dataclasses, one per manager, that are finally gathered into an environment configuration. The decorator @configclass turns each class into a dataclass whose mutable defaults are copied per instance, which is what allows configurations to be inherited and overridden safely.

RlStateSceneCfg
Declares every prim in the scene: the robot, the insertive object (the peg), the receptive object (the hole), the table, the ground plane, and a dome light. Each entry is an asset configuration with a USD path and physics properties. The string {ENV_REGEX_NS} in a prim path is expanded to one path per parallel environment.
BaseEventCfg
Startup-time randomisation of friction, mass, and gripper actuator gains, plus the reset term. TrainEventCfg adds reset_from_reset_states, which draws the initial state of every episode from the four recorded reset sets with equal probability. The evaluation variants draw only from the easiest set.
CommandsCfg
A single TaskCommand term. It does not command a goal pose. Its job is to read the assembled-pose metadata of the two objects and expose the success thresholds to the reward terms.
ObservationsCfg
Two groups. The policy group holds what a real robot can measure: previous action, joint positions, end effector pose, the two object poses, and the pose of the peg in the hole's frame. The critic group adds privileged quantities such as time left, velocities, masses, friction coefficients, and actuator gains.
RewardsCfg
Four small safety penalties on action magnitude, action rate, joint velocity, and abnormal robot states, then the task rewards described in the next section.
TerminationsCfg
Episodes end on time out or when the robot enters an abnormal state. Success does not end an episode, which lets the policy learn to hold the assembled pose.
Ur5eRobotiq2f85RlStateCfg
The assembly point. It names one instance of each manager configuration and sets the simulation step, decimation, episode length, and the PhysX solver settings that the sim-to-real transfer was validated against.

The remaining classes in the file are thin variants of the base configuration. Figure 3 shows how they relate. The training configuration uses the implicit actuator model and the broad reset distribution. The finetune configuration swaps in the explicit actuator model, adds the system identification randomisation, and turns on the curricula. The two evaluation configurations mirror those but freeze the randomisation and sample only the simplest reset set.

2.3 The action: relative Cartesian operational-space control

The policy does not output joint torques. It outputs a six-dimensional relative pose change for the end effector plus one scalar for the gripper. The RelCartesianOSCAction term scales each axis, integrates the change into a desired pose, and converts the pose error into joint torques with a task-space proportional-derivative law.

τ = Jᵀ ( Kp · epose + Kd · evel ) + τnull

The Jacobian comes from an analytical kinematic model of the calibrated robot rather than from the simulator, so the controller in simulation matches the controller running on the real arm. There is no inertia decoupling. The per-axis scales are part of the configuration and are reduced by the finetune curriculum, which makes the policy's steps smaller as it becomes more reliable. The gripper action is binary: a positive value commands the open joint target and a negative value commands the closed target.

2.4 The reward: progress toward the assembled pose

Every object in a task ships with a metadata.yaml file beside its USD. It records a bottom_offset, used to place the object flush on a surface, an assembled_offset, which is the frame that must coincide with the partner's frame when the parts are assembled, and the position and orientation tolerances that define success. The reward code never hard codes a task. It reads these two frames and measures their distance.

The ProgressContext term is unusual: its weight is nonzero but it always returns zero reward. It exists to compute shared quantities once per step and expose them as attributes. It transforms the peg's assembled frame into the hole's assembled frame, stores the translation distance and the roll-plus-pitch angular distance, and sets a boolean success flag when both are within tolerance. Yaw is ignored because the peg is symmetric about its axis. Two further terms read those attributes: dense_success_reward returns a smooth exponential of the two distances, and success_reward returns one whenever the flag is set. A fourth term rewards keeping the gripper near the peg. All terms are summed with the weights in RewardsCfg.

Because success is computed from object frames and metadata, adding a new task does not require new reward code. It requires a new pair of USD files with a correct assembled_offset, which is what the project's "Create a New Task" guide walks through.

3. Reset-state datasets

The idea behind OmniReset is that a policy can learn a long contact-rich task from a sparse success signal if its episodes start from a sufficiently diverse set of states, including states that are already partway through the task. Those states are not sampled at training time. They are recorded in advance by dedicated environments and stored as tensors, and the training environment's reset term simply writes one of them into the simulator.

3.1 How a reset set is recorded

Each set has its own registered task id and its own environment configuration in reset_states_cfg.py. These environments share the scene with the training environment but have no observations and no learned actions. Their event terms place the objects and the arm, and their single success termination decides whether the resulting state is worth keeping. An episode lasts two seconds. During that time the recorder holds the gripper command, and at the end the success term checks that the robot and both objects are at rest, that the gripper points roughly downward, that neither object has fallen below the table, that the objects did not drift from where they were placed, and that the robot does not interpenetrate the objects. For the sets in which the hand is supposed to be grasping, the check also requires that the fingers were stopped short of their closed position and that the peg is within reach of the end effector. States that pass are appended to the dataset.

A recorded state is the full scene state: the robot's root pose and joint positions and the root pose of every rigid object, including the table. The reset term writes all of it back. This has a practical consequence. If you move or replace the table in the scene configuration, the recorded datasets still contain the old table pose and will teleport the table back to it. Regenerate the datasets after any scene change.

3.2 Why success rates differ so much between sets

Set 1 succeeds in roughly half of the attempts because it only needs the dropped peg to come to rest. The grasped sets succeed far less often, because a randomly chosen grasp pose must be reachable by inverse kinematics, must not collide with the table, and must hold the peg through the two-second settle. On the cluster the pipeline runs 2048 environments per set and asks for 10,000 states, so even a success rate below one percent finishes in reasonable time. On a workstation it is better to request a handful of states per set.

4. The algorithm

The learning algorithm is proximal policy optimisation as implemented in the rsl_rl library. UWLab does not reimplement it. The repository contributes a configuration, a thin environment wrapper supplied by Isaac Lab, and a few extensions in uwlab_rl. Figure 5 shows the loop that OnPolicyRunner.learn executes.

4.1 The runner configuration

The configuration lives in config/ur5e_robotiq_2f85/agents/rsl_rl_cfg.py as the class Base_PPORunnerCfg. The G1-D variant subclasses it and changes only the experiment name. The table lists the settings that shape the learning problem.

SettingValueMeaning
Actor and critic networksMLP 512, 256, 128, 64 with ELUSeparate networks with the same shape. Both normalise their inputs with running statistics.
Action distributionHeteroscedastic Gaussian, log standard deviation bounded to [0.001, 2.0]The actor predicts a state-dependent standard deviation alongside the mean, so exploration can shrink where the policy is confident.
Observation groupsactor: policy, critic: policyThe runner maps both networks to the policy group. The privileged critic group is defined in the environment and available for experiments.
Rollout length32 steps per environmentShort relative to the 160-step episode, which relies on the critic's bootstrap.
Discount and GAEγ 0.99, λ 0.95Standard values for a 10 Hz control rate.
PPOclip 0.2, 5 epochs, 4 mini-batches, entropy 0.006, gradient norm 1.0The learning rate adapts to keep the KL divergence near 0.01.

4.2 Two training stages

Training happens in two stages that differ in the environment rather than in the algorithm. Stage 1 uses the implicit actuator model of Isaac Lab and no system identification noise. It learns the task. Stage 2 resumes from the stage 1 checkpoint in the finetune environment, which uses the explicit delayed motor model, randomises the arm's identified parameters and the controller gains, and shrinks the action scale. Two curriculum terms manage how quickly those changes are introduced. Each watches the success rate reported by the reset manager and increases its progress by one percent when the rate exceeds 0.95, or decreases it when the rate drops below 0.9. The result is a policy that was first trained in an easy simulator and then hardened in one that resembles the real robot.

4.3 What uwlab_rl adds

The module uwlab_rl/rsl_rl/rl_cfg.py defines extended algorithm configurations such as RslRlFancyPpoAlgorithmCfg, which supports behaviour cloning and DAgger-style terms for the distillation stage, and exporter.py turns a trained actor into a deployable file. These are used by the later stages of the project and are not needed to understand stage 1.

5. The entry points

Every program in this repository follows the same opening ritual: parse the command line, launch the simulator, and only then import anything that depends on it. The order is forced by Isaac Sim, whose Python modules do not exist until the application has started. Figure 6 traces scripts/reinforcement_learning/rsl_rl/train.py from the shell to the learning loop.

5.1 Task registration

A task id such as OmniReset-Ur5eRobotiq2f85-RelCartesianOSC-State-v0 is a key in the Gymnasium registry. The registration happens in config/ur5e_robotiq_2f85/__init__.py, and it does not point at a class. It points at two import strings: the environment configuration class and the agent configuration class. Nothing is instantiated until a script asks for the task, which keeps importing uwlab_tasks cheap even though it registers dozens of environments.

gym.register(
    id="OmniReset-Ur5eRobotiq2f85-RelCartesianOSC-State-v0",
    entry_point="isaaclab.envs:ManagerBasedRLEnv",
    disable_env_checker=True,
    kwargs={
        "env_cfg_entry_point": f"{__name__}.rl_state_cfg:Ur5eRobotiq2f85RelCartesianOSCTrainCfg",
        "rsl_rl_cfg_entry_point": f"{agents.__name__}.rsl_rl_cfg:Base_PPORunnerCfg",
    },
)

5.3 The pipeline scripts

docker/forge/g1d_pipeline.sh is the orchestration layer for the cluster. It runs inside the image, takes a comma-separated STAGES list of assets, datasets, and train, and caches the output of each stage on the shared blob disk so that a later job can skip finished work. FORCE=1 ignores the cache. docker/forge/run_local.sh starts the same image on a workstation with the working copy mounted over the code, forwards the display when one is available, and offers a smoke mode that runs the whole pipeline at small sizes in about twenty minutes. The README in that folder documents the knobs.

6. Case study: adding the Unitree G1-D

The G1-D variant is a good illustration of how the configuration system is meant to be extended, because it reuses the entire MDP of the UR5e task and changes only what the new robot forces it to change. Figure 7 lists the files that were added and what each one overrides.

Three lessons from that port are worth keeping in mind when you extend the code yourself. First, parent defaults should be read from an instance of the parent configuration rather than from the class, because configclass stores mutable defaults as factories. Second, when a variant inherits from two configuration classes, only the first base's __post_init__ runs automatically, so a variant that needs both must call the second one explicitly. Third, anything that changes the scene, including the table, invalidates the recorded reset-state datasets, because they store every rigid object's pose.

Glossary

term
A function or callable class that a manager invokes every step with the environment as its first argument. Configuration classes list terms by name, weight, and parameters.
configclass
Isaac Lab's dataclass decorator. It adds dictionary conversion, deep copies of mutable defaults, and a replace method for making variants.
insertive and receptive object
The part being inserted and the part receiving it. For peg insertion they are the peg and the hole. The names are used everywhere so that the same code serves all six tasks.
assembled offset
A frame stored in each object's metadata. The task is solved when the two objects' assembled frames coincide within the stored tolerances.
reset set
One of the four recorded distributions of initial states. The training reset term mixes them with equal probability.
decimation
The number of physics steps per policy step. Twelve steps at 120 Hz give a 10 Hz control rate.
implicit and explicit actuator
Two actuator models. The implicit one is a PD drive solved inside PhysX. The explicit one computes torques in Python each step and can add delays and limits that match the real motor.
